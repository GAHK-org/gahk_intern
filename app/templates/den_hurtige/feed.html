It covers Android and desktop; `.no-zoom` and the gesture handlers in frontend/src/feed.ts cover iOS. interactive-widget=resizes-content is about the SOFT KEYBOARD, and it is the one part of this meta that behaves differently on the two platforms. Chrome on Android defaults to `resizes-visual`: the keyboard shrinks the visual viewport but leaves the LAYOUT viewport alone, so 100dvh still measures the whole screen, the shell stays full height, and the composer — the last flex child, pinned to the bottom of that shell — sits behind the keyboard. {% comment %} The message list. Polled so other residents' messages appear without a refresh. MORPHED, not replaced: idiomorph patches the existing nodes rather than swapping the list out, so scroll position, open reply threads and a half-typed reply survive because they are simply never touched. That is what let the interval drop from 20s to 5s — at 20s a new message read as broken, and the old wholesale swap was too destructive to run any faster. The response is still the WHOLE list, deliberately. An incremental "only what is new" endpoint would be less traffic, but traffic was never the problem here (one request per tab per few seconds, at ~60 rooms), and sending everything is what keeps deletions, expiry, reaction counts and new replies correct without a second reconciliation path. {% endcomment %} {% comment %} Feed and thread panel side by side. On a phone only one is shown at a time -- the CSS hides #js-feed while a panel exists, rather than covering it with an overlay. That is not a style choice: an overlay needs position:fixed and a z-index, which makes a stacking context, and no ancestor of a `.pop` may create one or the emoji picker and the reader panels get trapped inside it (see the .pop block in styles.css). Swapping display keeps the panel an ordinary in-flow box, so the pickers still work from inside a thread -- and it takes the feed out of the accessibility tree properly, so the panel needs no aria-modal and no focus trap. {% endcomment %}
