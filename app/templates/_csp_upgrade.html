{% comment %} upgrade-insecure-requests — but only on a page that is itself HTTPS. Why it is here at all: legacy CMS bodies carry absolute http://gahk.dk/public/... image URLs, and on the production HTTPS site the browser blocks those as mixed content. Upgrading them in the browser is cheaper than rewriting every stored body. WHY IT IS CONDITIONAL: local development is http end to end, and the header does not care. A /media/ hit 302s to a presigned URL on MinIO's published port — http://localhost:9000 (core/media.py, core/storage.py) — and the browser upgrades that redirect to https://localhost:9000, where nothing is listening. Every photograph on Den Hurtige, opslagstavlen and the front page then fails to load, and nothing appears in the Django log, because the request never reaches us. It is the REDIRECT that gets upgraded, which is why this looked selective. Chromium leaves an http URL alone when it is loopback — it is already a potentially trustworthy origin — so fotoalbum, whose .url() hands the browser the presigned http://localhost:9000/... link outright (photo_album/storage.py), loads fine and looks like proof the header is harmless. A 302 to the same host does NOT get that exemption: measured in Brave, -> 302 -> http://localhost:9000/x never issues the second request at all, while the identical page without this header follows it. Den Hurtige, opslagstavlen and profile pictures all go through /media/, fotoalbum does not, and that is the whole difference. request.is_secure() is the right condition rather than `not settings.DEBUG`: SECURE_PROXY_SSL_HEADER (config/settings.py) makes it true behind the production proxy and false for plain http, which is exactly the set of pages that can have a mixed-content problem to begin with. {% endcomment %} {% if request.is_secure %}{% endif %}
